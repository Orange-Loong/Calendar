# 电子日历代码规范文档

## 一、文档概述

本文档定义了电子日历系统的代码规范，包括JavaScript/React/React Native代码的编写规则、命名约定、代码组织和最佳实践等。文档旨在确保团队成员编写的代码风格一致，提高代码的可读性、可维护性和可扩展性。

## 二、基本规则

1. **保持代码简洁**：避免不必要的复杂性和冗余
2. **代码可读性优先**：优先考虑代码的可读性，其次是性能
3. **遵循DRY原则**：Don't Repeat Yourself，避免重复代码
4. **遵循KISS原则**：Keep It Simple, Stupid，保持代码简单
5. **遵循SOLID原则**：面向对象设计原则
6. **使用语义化命名**：变量、函数、组件等命名应反映其功能
7. **添加必要的注释**：解释代码的目的和复杂逻辑
8. **定期进行代码审查**：确保代码质量和一致性

## 三、JavaScript/TypeScript语法规范

### 1. 缩进和换行

- 使用**2个空格**进行缩进
- 每行代码不超过**100个字符**
- 函数和类之间空**2行**
- 代码块之间空**1行**
- 操作符前后添加空格

**示例**：
```javascript
// 好的做法
function calculateSum(a, b) {
  return a + b;
}

class Calculator {
  constructor() {
    this.result = 0;
  }
  
  add(a, b) {
    this.result = a + b;
    return this.result;
  }
}
```

### 2. 命名约定

#### 2.1 变量和函数

- 使用**驼峰命名法**（camelCase）
- 变量名应反映其**用途**，避免使用单字母变量（循环变量除外）
- 函数名应使用**动词开头**，描述其**行为**

**示例**：
```javascript
// 好的做法
const userName = '张三';
const isAuthenticated = true;

function getUserInfo() {
  // 函数实现
}

function calculateTotalPrice(products) {
  // 函数实现
}
```

#### 2.2 类和组件

- 使用**帕斯卡命名法**（PascalCase）
- 类名应反映其**职责**
- 组件名应使用**名词或名词短语**

**示例**：
```javascript
// 好的做法
class UserService {
  // 类实现
}

function CalendarView() {
  // 组件实现
}

class EventForm extends React.Component {
  // 组件实现
}
```

#### 2.3 常量

- 使用**全大写**和**下划线**分隔（UPPER_CASE_WITH_UNDERSCORES）
- 常量应在文件顶部定义

**示例**：
```javascript
// 好的做法
const API_URL = 'https://api.example.com';
const MAX_ITEMS = 100;
const COLORS = {
  PRIMARY: '#007bff',
  SECONDARY: '#6c757d'
};
```

#### 2.4 文件命名

- **JavaScript/TypeScript文件**：使用**驼峰命名法**（camelCase）
- **React组件文件**：使用**帕斯卡命名法**（PascalCase）
- **样式文件**：使用**驼峰命名法**或**短横线分隔**（kebab-case）

**示例**：
```
// 好的做法
utils.js
userService.js
CalendarView.jsx
EventForm.jsx
styles.css
calendar-view.css
```

### 3. 注释规范

#### 3.1 单行注释

- 使用`//`进行单行注释
- 注释应在代码行的上方，或在代码行的右侧
- 注释应简洁明了，解释代码的**目的**，而不是**实现**

**示例**：
```javascript
// 好的做法
// 获取用户信息
const userInfo = getUserInfo();

// 计算总价格
const totalPrice = calculateTotalPrice(products); // 不含税费
```

#### 3.2 多行注释

- 使用`/* */`进行多行注释
- 用于函数和类的**文档注释**
- 包含函数/类的**描述**、**参数**、**返回值**和**示例**

**示例**：
```javascript
/**
 * 获取用户信息
 * @param {string} userId - 用户ID
 * @returns {Object} 用户信息对象
 * @example
 * const user = getUserInfo('123');
 */
function getUserInfo(userId) {
  // 函数实现
}
```

#### 3.3 JSDoc注释

- 对于公共API，使用JSDoc注释
- 包含**@param**、**@returns**、**@throws**、**@example**等标签

**示例**：
```javascript
/**
 * 计算两个数的和
 * @param {number} a - 第一个数
 * @param {number} b - 第二个数
 * @returns {number} 两个数的和
 * @throws {TypeError} 如果参数不是数字
 * @example
 * const sum = add(1, 2); // 3
 */
function add(a, b) {
  if (typeof a !== 'number' || typeof b !== 'number') {
    throw new TypeError('参数必须是数字');
  }
  return a + b;
}
```

## 四、React/React Native规范

### 1. 组件设计

#### 1.1 组件类型

- 优先使用**函数组件**和**Hooks**
- 对于复杂组件，考虑使用**类组件**或**React.memo**

**示例**：
```javascript
// 好的做法
function CalendarView() {
  const [view, setView] = useState('month');
  
  const handleViewChange = (newView) => {
    setView(newView);
  };
  
  return (
    <div>
      <ViewToggle view={view} onViewChange={handleViewChange} />
      {/* 日历实现 */}
    </div>
  );
}
```

#### 1.2 组件命名

- 组件名应使用**名词或名词短语**
- 组件名应反映其**功能**
- 避免使用通用名称（如`Component`、`Container`）

**示例**：
```javascript
// 好的做法
function CalendarView() { /* ... */ }
function EventForm() { /* ... */ }
function TaskList() { /* ... */ }

// 不好的做法
function Component() { /* ... */ }
function Container() { /* ... */ }
```

#### 1.3 Props命名

- Props名应使用**驼峰命名法**
- 布尔类型的Props名应使用**is**或**has**前缀
- 回调函数Props名应使用**on**前缀

**示例**：
```javascript
// 好的做法
function Button({
  isPrimary,
  isDisabled,
  onClick,
  onHover
}) {
  // 组件实现
}

// 使用示例
<Button
  isPrimary
  isDisabled={false}
  onClick={handleClick}
  onHover={handleHover}
>
  Click Me
</Button>
```

#### 1.4 状态管理

- 优先使用**组件内状态**（useState）
- 对于共享状态，使用**Context API**或**Redux Toolkit**
- 避免在组件间直接共享状态

**示例**：
```javascript
// 好的做法
function CalendarView() {
  const [events, setEvents] = useState([]);
  
  // 使用useEffect获取数据
  useEffect(() => {
    fetchEvents().then(data => setEvents(data));
  }, []);
  
  return (
    <div>
      {/* 日历实现 */}
    </div>
  );
}
```

#### 1.5 样式管理

**Web端**：
- 使用**CSS Modules**或**Styled Components**
- 避免使用**内联样式**（除了动态样式）
- 样式名应使用**驼峰命名法**或**短横线分隔**

**移动端**：
- 使用**StyleSheet API**
- 避免使用**内联样式**
- 样式名应使用**驼峰命名法**

**示例**：
```javascript
// Web端 - CSS Modules
import styles from './CalendarView.module.css';

function CalendarView() {
  return (
    <div className={styles.calendarContainer}>
      {/* 日历实现 */}
    </div>
  );
}

// 移动端 - StyleSheet API
import { StyleSheet } from 'react-native';

const styles = StyleSheet.create({
  calendarContainer: {
    flex: 1,
    padding: 16
  }
});

function CalendarView() {
  return (
    <View style={styles.calendarContainer}>
      {/* 日历实现 */}
    </View>
  );
}
```

### 2. Hooks规范

#### 2.1 Hooks使用规则

- 只在**函数组件**或**自定义Hook**中使用Hooks
- 只在**组件顶层**调用Hooks
- 按照**相同的顺序**调用Hooks

**示例**：
```javascript
// 好的做法
function CalendarView() {
  const [view, setView] = useState('month');
  const [events, setEvents] = useState([]);
  
  useEffect(() => {
    fetchEvents().then(data => setEvents(data));
  }, []);
  
  // 正确：在组件顶层调用Hooks
  if (view === 'month') {
    return <MonthView events={events} />;
  }
  
  return <DayView events={events} />;
}

// 不好的做法
function CalendarView() {
  // 错误：在条件语句中调用Hooks
  if (someCondition) {
    const [view, setView] = useState('month');
  }
  
  return <div>Calendar</div>;
}
```

#### 2.2 自定义Hook命名

- 自定义Hook名应使用**use**前缀
- Hook名应反映其**功能**

**示例**：
```javascript
// 好的做法
function useCalendarEvents() {
  const [events, setEvents] = useState([]);
  const [loading, setLoading] = useState(true);
  
  useEffect(() => {
    fetchEvents().then(data => {
      setEvents(data);
      setLoading(false);
    });
  }, []);
  
  return { events, loading };
}

// 使用示例
function CalendarView() {
  const { events, loading } = useCalendarEvents();
  
  if (loading) {
    return <LoadingSpinner />;
  }
  
  return (
    <div>
      {/* 日历实现 */}
    </div>
  );
}
```

## 五、后端Node.js规范

### 1. 项目结构

```
backend/
├── src/
│   ├── config/         # 配置文件
│   ├── controllers/    # 控制器
│   ├── middlewares/    # 中间件
│   ├── models/         # 数据模型

│   ├── utils/          # 工具函数
│   └── app.js          # 应用入口
├── .env               # 环境变量
├── package.json       # 项目配置
└── README.md          # 项目说明
```

### 2. 路由设计

- 路由文件应按照**功能模块**组织
- 路由路径应使用**短横线分隔**（kebab-case）
- 路由处理函数应放在**控制器**中

**示例**：
```javascript
// 好的做法
const express = require('express');
const eventController = require('../controllers/eventController');
const authMiddleware = require('../middlewares/authMiddleware');

const router = express.Router();

router.get('/events', authMiddleware, eventController.getEvents);
router.post('/events', authMiddleware, eventController.createEvent);
router.get('/events/:id', authMiddleware, eventController.getEventById);
router.put('/events/:id', authMiddleware, eventController.updateEvent);
router.delete('/events/:id', authMiddleware, eventController.deleteEvent);

module.exports = router;
```

### 3. 控制器设计

- 控制器函数应使用**动词开头**
- 控制器函数应只负责**请求处理**和**响应**
- 业务逻辑应放在**服务**中

**示例**：
```javascript
// 好的做法
const eventService = require('../services/eventService');

exports.getEvents = async (req, res) => {
  try {
    const events = await eventService.getEvents(req.user.id);
    res.json({ success: true, data: events });
  } catch (error) {
    res.status(500).json({ success: false, message: error.message });
  }
};

exports.createEvent = async (req, res) => {
  try {
    const event = await eventService.createEvent(req.user.id, req.body);
    res.status(201).json({ success: true, data: event });
  } catch (error) {
    res.status(400).json({ success: false, message: error.message });
  }
};
```

### 4. 错误处理

- 使用**try-catch**捕获异步错误
- 使用**统一的错误处理中间件**
- 错误信息应**友好**，不暴露系统细节

**示例**：
```javascript
// 好的做法
// 错误处理中间件
const errorHandler = (err, req, res, next) => {
  console.error(err.stack);
  
  const statusCode = err.statusCode || 500;
  const message = err.message || '服务器错误';
  
  res.status(statusCode).json({
    success: false,
    message: message
  });
};

// 使用错误处理中间件
app.use(errorHandler);
```

## 六、CSS/样式规范

### 1. CSS命名约定

- 使用**BEM**（Block-Element-Modifier）命名规范
- 或使用**短横线分隔**（kebab-case）
- 避免使用**ID选择器**
- 优先使用**类选择器**

**示例**：
```css
/* 好的做法 - BEM */
.calendar {
  /* 块样式 */
}

.calendar__header {
  /* 元素样式 */
}

.calendar__view-toggle {
  /* 元素样式 */
}

.calendar__view-toggle--active {
  /* 修改器样式 */
}

/* 好的做法 - 短横线分隔 */
.calendar-container {
  /* 容器样式 */
}

.calendar-header {
  /* 头部样式 */
}

.calendar-view-toggle {
  /* 视图切换样式 */
}

.active-view {
  /* 激活状态样式 */
}
```

### 2. 样式组织

- 按**功能模块**组织样式
- 避免使用**全局样式**
- 使用**CSS变量**管理主题和颜色

**示例**：
```css
/* 好的做法 - CSS变量 */
:root {
  --primary-color: #007bff;
  --secondary-color: #6c757d;
  --background-color: #f5f5f5;
  --text-color: #333;
}

.calendar {
  background-color: var(--background-color);
  color: var(--text-color);
}

.calendar__view-toggle--active {
  background-color: var(--primary-color);
  color: white;
}
```

### 3. 响应式设计

- 使用**媒体查询**实现响应式设计
- 优先使用**移动优先**的设计思路
- 使用**相对单位**（rem, em, %）

**示例**：
```css
/* 好的做法 - 移动优先 */
.calendar {
  padding: 10px;
}

@media (min-width: 768px) {
  .calendar {
    padding: 20px;
  }
}

@media (min-width: 1024px) {
  .calendar {
    padding: 30px;
  }
}
```

## 七、代码审查规范

### 1. 代码审查流程

1. 创建**Pull Request**
2. 至少**1个审查者**批准
3. 所有**CI检查通过**
4. 解决所有**审查意见**
5. 合并到目标分支

### 2. 审查要点

- **代码质量**：代码是否简洁、可读、可维护
- **功能正确性**：代码是否实现了预期功能
- **性能**：代码是否存在性能问题
- **安全性**：代码是否存在安全漏洞
- **测试覆盖**：代码是否有足够的测试覆盖
- **规范符合性**：代码是否符合项目规范

### 3. 审查反馈

- 反馈应**具体**、**建设性**
- 避免**主观判断**和**个人偏好**
- 提供**改进建议**，而不仅仅是指出问题
- 使用**礼貌**的语气

**示例**：
```
// 好的反馈
"这个函数可以考虑使用async/await来简化异步逻辑，提高可读性。"

"建议将这个复杂的条件判断提取为单独的函数，使代码更清晰。"

// 不好的反馈
"这段代码写得太复杂了。"
"我不喜欢这种写法。"
```

## 八、测试规范

### 1. 测试类型

- **单元测试**：测试单个函数或组件
- **集成测试**：测试多个组件或模块的交互
- **端到端测试**：测试整个应用的流程

### 2. 测试覆盖率

- **目标覆盖率**：
  - 语句覆盖率：≥ 80%
  - 分支覆盖率：≥ 70%
  - 函数覆盖率：≥ 80%
  - 行覆盖率：≥ 80%

### 3. 测试框架

- **前端**：Jest, React Testing Library, Cypress
- **后端**：Jest, Supertest, Mocha

### 4. 测试命名

- 测试文件名应与被测试文件对应，添加`.test`或`.spec`后缀
- 测试用例名应使用**描述性**的名称
- 测试用例名应反映**预期行为**

**示例**：
```javascript
// 好的做法
// calendarView.test.js
import { render, screen } from '@testing-library/react';
import CalendarView from './CalendarView';

describe('CalendarView', () => {
  test('should render month view by default', () => {
    render(<CalendarView />);
    expect(screen.getByText('Month')).toHaveClass('active');
  });
  
  test('should switch to week view when week button is clicked', () => {
    render(<CalendarView />);
    const weekButton = screen.getByText('Week');
    weekButton.click();
    expect(weekButton).toHaveClass('active');
  });
});
```

## 九、Git规范

### 1. 分支管理

- **main**：主分支，稳定版本
- **develop**：开发分支，集成所有功能
- **feature/**：功能分支，开发新功能
- **hotfix/**：热修复分支，修复生产环境问题
- **release/**：发布分支，准备发布新版本

### 2. 提交信息

- 使用**Conventional Commits**规范
- 提交信息格式：`<type>(<scope>): <description>`

**类型**：
- feat：新功能
- fix：修复bug
- docs：文档更新
- style：代码格式调整
- refactor：代码重构
- test：测试代码
- chore：构建过程或辅助工具的变动

**示例**：
```
feat(web): 添加日历月视图
fix(mobile): 修复任务列表渲染问题
docs: 更新开发环境配置文档
style: 调整代码格式
refactor: 重构事件处理逻辑
test: 添加单元测试
chore: 更新依赖版本
```

### 3. 提交频率

- 每个**有意义的修改**都应提交
- 提交应**小而频繁**
- 避免**大爆炸式**提交
